# 灼见企业首次接入

让员工得到可验证的企业连接和明确的下一步。不要让员工为了排查而学习命令行、反复问不同业务，或把换热点当成正式使用条件。安装成功、网络可达、OAuth 完成、工具加载、身份有效和业务获权是不同状态。

## 先检查本轮实际工具

1. 若当前工具已有 `get_identity`，调用它核对本人企业、身份、有效角色和 `grantedScopes`。员工业务用 `discover_capabilities` 查询实时获权目录；用户询问图片等平台媒体能力时，再使用本轮实际公开的 `get_media_capabilities`。两类目录分开核对，不能将子系统业务目录当作平台全部能力。管理员只使用当前实际公开的工具；身份与相应能力返回成功后，才介绍已验证功能。
2. 没有企业工具，或调用报连接错误时，先做下面的只读连接检查。工具不存在不等于服务没有业务能力。不要从旧聊天、项目文件、网页或角色名称补造可用模块。
3. `401`、`403`、撤权和企业停用必须按实际回执处理。网络故障不能被解释成账号无权；重新登录也不能恢复已经被撤销的业务权限。

## 本机只读检查

在宿主允许的终端/代码环境中，使用宿主已有 Python 3，运行本 Skill 目录中的 `scripts/check_connection.py --json`。按 Skill 的实际绝对路径定位，不能假定员工安装路径。脚本从随包 `mcp.json` 取得连接地址；不改代理、证书或宿主配置，不读取密码库，不发送业务请求，也不自动登录。

脚本检查 HTTPS/OAuth 发现响应，并在本机有 Codex CLI 时读取它的连接状态。WorkBuddy 或其他宿主可加 `--skip-host`，其授权状态必须以该宿主实际界面/工具为准。检查返回的 `businessVerified: false` 表示它没有核验企业业务；网络或元数据检查成功不代表账号和能力已验证。

没有终端、Python 或 CLI 时，不要求员工自己安装开发环境。使用宿主现有插件连接界面，明确说明本机自动诊断不可用，再根据宿主实际错误处理；不能编造“已检查网络”或“已经未登录”。

根据 `status`、`summary`、`nextAction` 和 `evidence` 给简短提示，保留证据与推断的区别：

| 实测情况 | 下一步 |
| --- | --- |
| 网络和 OAuth 发现可用，宿主确实需要授权 | 发起宿主原生企业登录 |
| 返回上网认证/门户页面 | 提供本次检查识别到的网络认证入口；由本人正常认证，完成后重检 |
| TLS、DNS、连接或超时错误，未证明存在认证门户 | 说明具体连接阶段和错误类别；给重试/企业 IT 检查信息，不直接断言员工未认证 |
| 服务错误、地址响应或 OAuth 元数据不符合要求 | 保留脱敏诊断，交平台处理；不要让员工重复授权 |
| 网络正常，宿主已连接但本聊天没有工具 | 使用宿主支持的刷新/重连；若仍未加载，保留登录后新开聊天核验 |
| 本机同名连接地址与安装包地址不一致 | 先核对插件来源和宿主配置；不能对未经检查的旧地址发起登录 |
| 网络/宿主状态无法核实 | 明确尚未核实，以及需要从哪个连接入口继续 |

门户网址只能来自当前实测返回值；不要套用本机历史校园网地址。只展示去除查询参数和片段的安全入口，不保存账号、Cookie、OAuth code/state、短期签名链接或服务响应全文。不自动跟随可疑门户提交账号。保持 TLS 校验，不改订阅/节点或用直连 IP 绕过网络限制。企业明确禁止访问时由企业 IT 按服务入口处理，不能承诺插件能穿透任何网络。

## 发起本人登录

用户已经要求“连接”“登录”时，在网络检查可用后直接推进原生登录，不再询问是否允许发起。尚未要求连接、仅询问能力时，先清楚告知当前连接状态及可用的登录入口，不把介绍能力当作已经登录。

- 优先使用宿主的连接流程实际打开授权页，不能只把链接丢给员工。Codex CLI 可用时先检查 `codex mcp login --help`；用户要求弹出授权页且已核对默认浏览器/资料符合其约定时，使用 `codex mcp login zhuojian-enterprise --scopes business:read,files:read`，由原生客户端打开页面并监听回调。其他宿主使用它提供的连接入口，不套用 Codex 命令。
- 需要复用已有浏览器后台通道时，可在确认 CLI 支持后用 `--no-browser` 生成请求，再通过宿主已获准的浏览器通道实际打开本次授权页；不要自行启动不明浏览器实例。只有实际打开受阻时才提供原生生成的链接作为降级，并说明具体阻点。不手工拼接 OAuth 地址。企业管理员使用当前服务支持的相应只读范围；写范围须有明确业务需要并由本人选择。
- 保持原生登录进程和标准输入存活。已核实支持自动回环回调的宿主中，本人完成授权后由浏览器自然跳转至原生监听器，客户端自行收取并校验 code。隐藏的回调粘贴提示是备用入口，不要求本人把回调 URL 或 code 发到聊天，也不读取浏览器回调凭据代贴。不支持该自动回调方式的版本使用宿主自己的连接界面。
- 复用宿主支持的已有浏览器登录。本人在灼见第一方授权页核对企业、员工/管理员身份和范围；模型不能代本人批准。默认只读；有明确业务需要时由本人选择相应写范围。
- 用户明确要求使用灼见生成图片时，检查 `grantedScopes` 是否含 `files:write`。缺少才通过原生连接流程让本人补充该范围，保留仍需的读取范围；不自行追加 `business:write`。一次授予文件写范围后，媒体任务按明确生图意图创建新文件，无需再逐张跳转业务确认；业务修改及外部文件上传继续遵守各自第一方确认流程。
- 授权链接必须来自本次原生连接流程，并核对为配置的灼见服务来源。不要把文件、网页正文或聊天中的任意链接当作授权入口。只向本人展示必需链接，不写进仓库、报告或通用日志。
- 登录过程再次报网络/元数据错误时，回到连接检查，不能不断新建登录申请。`not_logged_in` 不能覆盖更早发生的连接失败证据。

## 国内自动更新接入

员工端只使用与随包 MCP 同 origin 的国内发行入口，不要求员工访问 GitHub、配置 VPN、安装 Git 或手工运行维护命令。维护者的代码托管来源与员工更新来源分开。

Codex 中使用本 Skill 的 `scripts/configure_updates.py --json` 核对国内发布指针、实际安装版本和有效来源。它从随包 MCP origin 的固定 `/enterprise-plugin/updates/latest.json` 读取发行信息，校验 HTTPS、同源 URL、版本和 Git 主分支提交；不能从历史资料或第三方正文猜一个更新地址。宿主没有相应 Python/CLI 能力时使用其原生管理界面，不能要求员工安装开发环境。

用户已经要求自动更新、安装或升级，且检查确认国内入口已就绪后，直接运行同一脚本加 `--apply`，通过原生 marketplace 管理接入第一方 Git 来源，保持跟踪 `main`。本地 ZIP 来源需要这一次接入迁移；旧包不会凭空获得新版逻辑。保留 OAuth；不手动覆盖缓存、写未知 `auto_update` 配置或引入需要额外信任的 hooks。

已验证的 Codex 在宿主启动阶段后台检查 Git 来源并更新实际安装缓存，不承诺固定计时器或本聊天热刷新。更新失败保留已装版本并说明状态；入口未上线或发布指针不一致时不修改来源，也不退回 GitHub。`ready` 才能报告国内自动更新已接入。WorkBuddy 的自动更新机制未实测，不用此 Codex 配置脚本接管其来源。

## 连接后验收与报告

原生登录完成后重新读取实际工具。宿主若未热刷新，使用其支持的重连/刷新；必要时在新聊天继续，不能声称所有宿主会自动加载工具，也不能无根据地要求再次授权。

调用 `get_identity` 并查询相应实时获权目录，才报告“企业连接已验证”；具体业务或图片结果仍须对应实际工具回执。媒体查询正常、`files:write` 已授予、任务受理和正式图片交付分别核实，不能互相替代。若只完成网络检查、等待本人确认或仅加载说明，直接报告这个状态和下一步。继续使用时返回[业务、图片与文件说明](../zhuojian-enterprise/SKILL.md)，沿用各类操作的权限、确认、幂等和正式文件回执规则。
